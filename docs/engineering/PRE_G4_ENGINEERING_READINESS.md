# G4 前工程化与可运行性审计

> 审计日期：2026-09-02  
> 结论范围：独立重构仓库 `codex/systematic-refactor`；不代表生产发布批准，也不代表 G4/G5 已开始。

## 结论

当前 G0～G3.5 以及企业资料合并检查点均已完成。重构后项目能够在隔离的代表性本地完整栈中构建、启动、登录并完成已覆盖业务；当前自动化范围内没有未处理的阻断错误。

这个结论不能扩大为“三家企业已经可以上线”。真实 AI、三家企业配置包、客户数据迁移、破坏恢复演练、不可变制品和生产可观测性仍未完成，分别属于 G4/G5。

## 当前是否能运行

可以在已验证的本地工程环境运行。完整栈由 PostgreSQL、PostgREST、Agent Runtime、基座 Vite 和企业站 Vite 组成，真实登录和企业资料生命周期均已通过。企业资料测试结束后自动恢复 `company_site` Schema，并核对恢复结果为君乐缘已发布 v1；测试端口未留下 Vite 监听，原始仓库保持干净。

不能据此直接部署生产。当前证据没有覆盖生产网络、真实域名和证书、企业密钥、真实 AI 上游、客户数据量、灾难恢复时长或生产告警链路。

## 已观察到但不阻断的错误与告警

- 规范发布工具链是 Node 20.19.0/npm 10.8.2；本轮部分复核运行在兼容范围内的 Node 26.1.0/npm 11.13.0，正式发布前仍需使用规范工具链重跑。
- 前端构建存在循环 chunk、大包和部分第三方弃用告警，但 12/12 构建成功；这些告警不能被当作已解决。
- Agent 镜像重建后的第一次完整栈验收出现一次本机 Vite 到 Agent 的瞬时 `ETIMEDOUT`。直接请求随即返回 200，后续完整复跑通过，数据库自动恢复且未复现。它不是当前阻断项，但应在 G5 通过启动就绪探针、超时指标和告警治理。
- 107 份 SQL 中只有 Runtime V2 的 10 份和 company-site 的 1 份进入 Manifest 治理；其余历史 SQL 不允许按文件名自动执行。

## 仍需进行的功能性测试

进入 G4 后，至少需要用同一个版本制品分别验证伦度机电、君乐缘和经纬网厂：

1. 配置包 Schema、模块依赖、版本、校验和与审计信息。
2. 登录品牌、菜单/路由、功能开关和禁用模块失败关闭。
3. 企业站品牌、公开内容、域名、草稿、发布、停用和素材完整性。
4. 各企业实际启用的核心业务链、角色权限和空数据/真实样本数据边界。
5. 三套配置切换时 JS/CSS 制品哈希保持一致，源码不存在客户名称分支。

进入 G5 后还需要完成真实 AI、升级/回滚、破坏恢复、性能、安全、可靠性、日志指标和告警的发布级测试。

## 决策边界

当前最安全的停点是维持 G0～G3.5 门禁并等待是否进入 G4。若进入 G4，应先建立“企业配置包制品契约和校验器”，再逐家补充配置与测试；不应从复制三个客户分支或直接写入客户生产数据开始。
