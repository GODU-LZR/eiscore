## 每个问题的流程

1. 统筹窗口在 `LOCAL_TEST_ISSUES.md` 记录 `EIS-001` 起的编号、现象、期望、负责人、验收条件和状态；执行窗口回报数据，由统筹串行维护台账。
2. 分配消息必须包含问题号、源码基线、分支、工作树、允许修改文件/接口、验收方式和复核人。跨层问题拆分子任务；同文件重叠先通知再分配，不能两边同时抢改。
3. 执行窗口在独立任务分支复现、最小修复、对应测试；构建只写自己的目录，保留失败与未验证事实。不得启动旧的历史全局目标或自行修未分配的问题。
4. 每个完成验证的小改动单独提交，说明问题与结果，并运行 `git diff --cached --check`；仅推送本任务分支到 `eiscore`，不得强推、不得推到 DeepSeek 的 `origin` 或占位 `upstream` push URL。
5. 完成后通知统筹：问题号、提交号、分支、修改文件、真实测试结果、限制、制品路径、本地是否生效。另一执行窗口按分配交叉复核。
6. 统筹在重构分支串行 cherry-pick/合并已复核提交，检查冲突与组合回归，再推送 `eiscore/codex/systematic-refactor`。不能把任务分支已推送误报成主分支已整合。
7. 用户人工验收后记录通过或重新打开。状态分开记录“源码已修复 / 任务分支已推送 / 主分支已整合 / 本地已生效 / 用户验收”，禁止混用。

默认准备分支为 `codex/collab-{backend|frontend|site}-20261013`，仅用于接入确认；问题实施使用统筹分配的 `codex/fix-eis-NNN-职责` 分支，从当时最新整合基线创建。
新任务开始前检查工作树状态；旧任务不干净时先通知，不能强制切换或覆盖。推送命令显式指定分支，不能依赖隐式 remote。
