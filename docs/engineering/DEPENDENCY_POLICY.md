# 依赖与运行时治理策略

## 标准工具链

`config/toolchain.json` 是 CI 与发布证据使用的标准版本来源。当前固定 Node 20.19.0 和 npm 10.8.2；`.nvmrc`、`.node-version`、根 `package.json` 与 GitHub Actions 必须和它一致。

开发环境可以处于根 `engines` 声明的兼容范围，但非标准版本只适合日常编辑和快速验证。干净安装、发布候选验证和可追溯构建必须使用标准工具链：

```bash
npm run toolchain:check -- --strict
```

## 锁文件契约

- 根包、平台包、11 个前端和 `realtime` 共 14 个 CI 包必须提交 `package-lock.json`。
- 锁文件统一使用版本 3，包名必须与对应 `package.json` 一致。
- `npm run ci:install` 只接受锁文件安装；缺失锁文件立即失败，不得退化为 `npm install`。
- 生成物、`node_modules`、安装缓存和本地审批状态不得提交。

## 安装脚本与供应链

不得为了消除 npm 告警而全局批准第三方安装脚本。需要执行安装脚本的依赖必须先确认用途、版本、来源和构建必要性，再以独立变更记录决策。当前 npm 11 对部分依赖给出审批告警，但标准 npm 10 工具链和现有前端构建仍是发布判断依据。

## 升级规则

1. 运行时大版本、包管理器或 lockfile 格式升级必须先写 ADR。
2. 一次只升级一个依赖家族，不与业务功能或结构重构混合。
3. 使用标准 npm 版本更新 lockfile，并说明直接依赖与传递依赖变化。
4. 至少执行质量门禁、相关特征测试和受影响前端构建；公共构建依赖变更执行完整 `test:ci`。
5. 安全公告先评估可利用性和影响面，不使用无审查的自动大版本升级。
6. 升级无法保持兼容时必须提供迁移与回退说明。
